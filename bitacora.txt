Mi bitacora de Rueda Libre

Esto es mi bitacora del proyecto. La hice para anotar lo que probé, lo que aprendí y las decisiones que tomé en la pagina. Me sirve para recordar cómo quedó todo y por qué lo hice así.

1. Estructura del proyecto
Creé la carpeta del proyecto y guardé la pagina principal y las páginas de reservas y tarifas. También dejé la hoja de estilos y la carpeta de imágenes.

- index.html: pagina principal
- paginas/reservas.html: formulario para reservar
- paginas/tarifas.html: precios y paquetes
- css/styles.css: estilos visuales
- img/: imagenes del sitio

2. Prueba del sitio en DevTools
Abrí la pagina con Live Server y revisé la pestaña Network en DevTools. Allí pude ver cómo el navegador hace la petición para cargar la pagina.

Datos que anoté:
- URL completa: http://127.0.0.1:5500/index.html
- Protocolo: http
- Host: 127.0.0.1
- Puerto: 5500
- Ruta: /index.html
- Metodo: GET
- Codigo: 200

El codigo 200 significa que la pagina cargó bien.

3. Prueba de una ruta que no existe
También probé entrar a una dirección que no existe, por ejemplo:
- http://127.0.0.1:5500/promociones.html

Resultado: 404.
Esto quiere decir que la pagina no fue encontrada, porque esa ruta no está creada.

4. Qué hace cada lenguaje
HTML: estructura la pagina y organiza el contenido.
CSS: da estilo, colores y diseño visual.
JavaScript: hace la pagina más interactiva.

5. Rutas del sitio
Las paginas están relacionadas entre sí por enlaces:
index.html -> Tarifas -> paginas/tarifas.html
index.html -> Reservas -> paginas/reservas.html
paginas/reservas.html -> Inicio -> ../index.html
paginas/tarifas.html -> Reservas -> reservas.html

Esto ayuda a navegar mejor entre las secciones.

6. Justificación de algunos elementos
Reemplacé varios elementos por etiquetas semánticas como nav, header, main, section y footer porque tienen un significado más claro para la estructura de la pagina. Eso ayuda a que el sitio sea más ordenado y más fácil de entender.

Algunos div y span se quedaron porque solo sirven para organizar la visualización o darle estilo. No aportan contenido semántico, pero sí ayudan a que la pagina se vea bien. Por eso su uso está justificado.

7. Elección de controles del formulario
En el formulario decidí usar diferentes tipos de entrada según la información que necesitaba el cliente.

Nombre completo: usé un input tipo texto porque es una respuesta libre.
Tipo de documento y tipo de bicicleta: usé select porque son opciones predefinidas y el usuario debe elegir una sola.
Comentarios: usé textarea porque el cliente puede escribir una respuesta más larga y detallada.

También usé otros controles adecuados para cada dato: email para correos, date para fechas, number para cantidades y checkbox para aceptar políticas.

En resumen el formulario quedó más claro y más fácil de usar porque cada campo está pensado para el tipo de información que pide.
En DevTools (Styles y Computed), comprueba qué propiedades hereda un párrafo desde el cuerpo. Registra en la bitácora una propiedad que se hereda y una que no, comprobadas en tu sitio.

8. Mapa de uso de color y contraste
En este proyecto usé una paleta de colores clara y legible para mantener la identidad del sitio y también cumplir con una buena accesibilidad.

Texto principal: azul noche (#14213D)
Fondo general: crema (#FAF6EF)
Títulos y textos importantes: azul noche sobre fondo crema
Botones principales: verde ruta (#1E7A4F) con texto crema (#FAF6EF)
Botones en hover: naranja pedal (#F39A2B) con texto azul noche (#14213D)
Enlaces: verde ruta para el estado normal y azul noche para hover o foco
Fondo de secciones destacadas: verde ruta con texto crema
Texto secundario e información complementaria: gris asfalto (#5B6470) sobre fondo crema

Clasificación de combinaciones:
Azul noche sobre crema: apta para texto normal
Gris asfalto sobre crema: apta para texto normal
Verde ruta sobre crema: apta para texto normal
Azul noche sobre naranja: apta para texto normal
Verde ruta sobre azul noche: no apta para texto normal
Naranja sobre crema: no apta para texto normal

Esto me ayudó a decidir qué combinaciones usar en texto, botones, fondos y enlaces para que fueran legibles y agradables visualmente.

9. Hallazgos de accesibilidad y correcciones
La bitácora registra al menos cinco hallazgos de accesibilidad y cómo los corregí

El texto alternativo del logo y del mapa no describía bien su función. Lo corregí para que fuera más claro: "Logo de Rueda Libre" y "Mapa de rutas para recorrer Medellín en bicicleta".
La navegación no tenía un nombre claro para lectores de pantalla. Agregué aria-label="Navegación principal" en las páginas principales.
En la portada había un enlace dentro de un botón, lo cual no es adecuado. Lo cambié para que fuera un enlace con estilo de botón, sin anidar controles.
Las opciones de duración del alquiler estaban sueltas. Las agrupé con fieldset y legend para que la intención del grupo fuera más clara.
Los enlaces y botones no tenían un foco visible claro al navegar con teclado. Añadí un contorno visible para mejorar la accesibilidad.
El contraste del texto en algunos enlaces no era suficiente. Ajusté los colores para que fueran más legibles, especialmente en los botones y enlaces.

Con estos cambios, la pagina quedó más fácil de usar para personas que navegan con teclado o con lectores de pantalla.

10. Herencia de CSS en DevTools
En DevTools revisé un párrafo del sitio para comprobar qué propiedades hereda desde el body y cuáles no.

Propiedad que sí se hereda:
- color: el body tiene color: var(--azul-noche); y el párrafo lo hereda, por eso el texto del párrafo aparece en azul oscuro sin que lo declare directamente.
- font-family: el body tiene font-family: 'Poppins', sans-serif; y el párrafo también la hereda, por eso usa la misma fuente del sitio.

Propiedad que no se hereda:
- background-color: el body tiene background-color: var(--crema), pero el párrafo no lo hereda, porque el fondo de la página no se aplica automáticamente al texto o al bloque del párrafo.

Esto lo comprobé en Styles y Computed: el párrafo toma el estilo del body en algunas propiedades, pero no en todas. La herencia ayuda a ahorrar código y mantener el diseño uniforme.

13. MiniReto 2 · Tailwind con la CLI y botones
Instalé Node.js (v26 LTS) y dentro de nocturna/ ejecuté:
- npm init -y
- npm install tailwindcss @tailwindcss/cli   (versión 4.3.5)
Creé src/input.css con @import "tailwindcss"; y un .gitignore con node_modules/.
En package.json dejé dos scripts:
- npm run dev   -> npx @tailwindcss/cli -i ./src/input.css -o ./src/output.css --watch
- npm run build -> lo mismo pero con --minify (para publicar)
Con --watch la CLI queda escuchando: cada vez que guardo un .html vuelve a generar src/output.css.

Qué encontré al buscar en output.css:
- Clase que uso: bg-amber-400 SÍ aparece (.bg-amber-400 { background-color: var(--color-amber-400); }) y también la variable --color-amber-400 en la capa theme.
- Clase que no uso: bg-pink-500 NO aparece, ni siquiera la variable --color-pink-500.
Por qué ocurre: la CLI escanea mis archivos (html) buscando nombres de clases y solo genera el CSS de las que encuentra. Las variables del tema también se recortan si no se usan. Por eso el archivo pesa ~16 KB y no los megas que tendría Tailwind completo. Consecuencia práctica: las clases tienen que estar escritas completas en el HTML (no armarlas concatenando textos), o no se generan.

Botones: principal, secundario y de contorno, todos con hover: (cambian de color y sombra) y focus:. Como quité el contorno del navegador con focus:outline-none, lo reemplacé por un anillo visible: focus:ring-4 + focus:ring-offset-2 (Verde Ruta en modo claro, Amarillo Farol en modo oscuro).
Prueba con teclado (confirmar a mano): con Tab el foco debe recorrer en orden logo -> enlaces -> botones; cada botón debe mostrar el anillo y Enter activa el enlace.

15. MiniReto 4 · Kit de componentes (nocturna/componentes.html)
La página reúne: los tres botones, una card de ruta, las tres etiquetas de nivel, tres alertas y dos campos.
- Alertas: fondo suave (color/10 o /15), borde lateral border-l-4 del color, título en negrita y texto. La de éxito tiene role="status": así el lector de pantalla la anuncia como un aviso (de forma educada, sin interrumpir), que es lo correcto para una confirmación. role="alert" lo reservaría para errores urgentes.
- Campos (correo y celular): <label for="..."> visible asociado al id del input, borde, relleno px-4 py-3, placeholder de ejemplo, texto de ayuda debajo conectado con aria-describedby, y foco visible (cambia el borde + anillo ring-4).

Reglas del kit:
- Radios: rounded-xl en botones, campos y alertas; rounded-2xl en cards y contenedores; rounded-full en etiquetas/píldoras.
- Espaciado: solo la escala 2 · 4 · 6 · 8 (8/16/24/32 px). Botones px-6 py-3, campos px-4 py-3, cards p-6, separaciones gap-4 o gap-6.
- Colores: solo los seis de la marca (ver MiniReto 7). Foco siempre con anillo Verde Ruta (claro) / Amarillo Farol (oscuro).

Publicación: pendiente de hacer commit + push y revisar en línea https://<usuario>.github.io/<repo>/nocturna/componentes.html

16. MiniReto 5 · Layout de la landing
Estructura semántica: <header>, <main> con una <section> por bloque (#inicio, #rutas, #como-funciona, #inscripcion) y <footer>. Los enlaces del menú usan esas anclas.
Contenedor común en todas las secciones: max-w-6xl mx-auto px-4 sm:px-6 lg:px-8.
Encabezado con flex: justify-between + items-center (logo a la izquierda; enlaces y botón "Inscríbete" a la derecha).
Rutas: grid con grid-cols-3 y gap-6.
"¿Cómo funciona?": elegí GRID (grid-cols-4) y no flex porque son cuatro tarjetas que deben tener exactamente el mismo ancho y alinearse en filas y columnas; con grid controlo el número de columnas por breakpoint (1/2/4) en una sola clase, mientras que con flex tendría que calcular anchos (basis) y los textos de distinto largo deformarían las cajas.
Pie: tres bloques (marca, contacto, horario) con flex y justify-between.
Copié los componentes de componentes.html sin crear variantes nuevas.

18. MiniReto 7 · Tema de la marca y modo oscuro
En src/input.css definí con @theme:
- --color-verde-ruta #1E7A4F, --color-naranja-pedal #F39A2B, --color-azul-noche #14213D, --color-crema #FAF6EF, --color-gris-asfalto #5B6470 (los cinco del sitio) y --color-amarillo-farol #FFD166 (campaña).
- --font-montserrat y --font-open-sans, cargadas desde Google Fonts (link en el <head>).
Tailwind genera solo las utilidades: bg-verde-ruta, text-amarillo-farol, border-gris-asfalto, font-montserrat, etc. Reemplacé todos los colores genéricos (slate, amber, emerald) en index.html y componentes.html; comprobé con una búsqueda que no queda ninguno.
Modo oscuro con dark: (estrategia por defecto, prefers-color-scheme): fondo azul-noche, texto crema, cards crema/5 con borde crema/15, campos con fondo azul-noche y borde crema/40, botón principal amarillo farol.

|------------------------------------|-----------|---------------------------|
| Verde Ruta sobre Azul Noche        | 3,01:1    | NO cumple -> corregido    |
| Gris Asfalto sobre Azul Noche      | 2,66:1    | NO cumple -> corregido    |

19. MiniReto 8 · Legibilidad (@apply) y Bootstrap vs Tailwind
Listas de clases más repetidas en index.html (antes de @apply):
- Botón principal: 6 veces (31 clases cada vez).
- Nombre del dato de la card (text-xs uppercase tracking-wide ...): 9 veces.
- Valor del dato (text-lg font-semibold): 9 veces.
- Texto secundario (text-gris-asfalto dark:text-crema/80): 6 veces.
- Caja de paso (p-6 rounded-2xl border ...): 4 veces. Número del paso: 4 veces.
- Card de ruta, etiqueta de nivel, precio: 3 veces cada una. Enlaces del menú: 3. Campos: 2.
Decisión: solo los botones (un único elemento que se repite mucho) pasaron a @layer components con @apply, en tres clases: .btn-primario, .btn-secundario, .btn-contorno. Las piezas grandes (cards, alertas, campos) mantienen el marcado del kit copiado igual en todos lados.
Dentro de cada clase ordené las utilidades por categoría: layout -> espaciado -> bordes -> tipografía -> color -> estados (hover, focus, dark).
Resultado: index.html bajó de 25.583 a 21.386 bytes y cada botón ahora es class="btn-primario".

Medición del CSS (npm run build = --minify):
- output.css minificado SIN @apply: 22.849 bytes
- output.css minificado CON @apply: 28.366 bytes (~4,9 KB con gzip)
  Ojo: @apply no ahorra CSS, al contrario: copia las declaraciones dentro de cada clase propia. Mejora la legibilidad del HTML, no el peso; por eso hay que usarlo con moderación.
- Sitio v2.0 con Bootstrap 5.3.8 (lo que descarga el navegador, CDN jsDelivr):
  bootstrap.min.css 232.111 bytes (~30,9 KB gzip)
  bootstrap.bundle.min.js 80.496 bytes (~23,7 KB gzip)
  bootstrap-icons.min.css 87.008 bytes (~13,5 KB gzip) + la fuente de iconos
  css/styles.css propio 3.787 bytes
  Total ≈ 403 KB sin comprimir (~68 KB gzip) frente a 28 KB (~5 KB gzip) de Tailwind y 0 KB de JavaScript.
  (Confirmar en DevTools > Network con "Disable cache": columnas Size/Transferred.)

Comparativa Bootstrap vs Tailwind:
| Criterio              | Bootstrap (v2.0)                                                                 | Tailwind (Rueda Nocturna)                                                              |
|-----------------------|----------------------------------------------------------------------------------|----------------------------------------------------------------------------------------|
| Curva de aprendizaje  | Más rápida al inicio: copias navbar, card, carrusel y funciona.                  | Más lenta al inicio (muchas utilidades, CLI, Node), pero luego se avanza muy rápido.   |
| Personalización       | Tuve que pisar variables --bs-* y clases (.btn-success, .card) para la marca.    | @theme con mis 6 colores y 2 fuentes; todo sale con nombre propio y modo oscuro dark:. |
| Tamaño final          | ≈ 403 KB (~68 KB gzip) aunque use una parte; incluye JS.                         | 28 KB (~5 KB gzip), solo las clases usadas; 0 JS.                                      |
| Casos de uso          | Sitios con componentes interactivos listos (modal, carrusel, menú hamburguesa).  | Diseños propios de marca, landings, sitios donde importa el peso y el control visual.  |

Recomendación para Rueda Libre: Tailwind. El cliente quiere su identidad visual (colores, fuentes, Amarillo Farol, modo oscuro) y el tráfico llega casi todo desde celulares: Tailwind me dio un CSS ~13 veces más liviano, sin JavaScript, y el tema de la marca quedó en un solo lugar (@theme). Lo que Bootstrap resolvía con JS (menú hamburguesa, carrusel, modal de políticas) se puede reemplazar con <details>, scroll-snap o <dialog> nativos y un poco de JS. La condición es mantener el kit de componentes y las reglas del kit para que el HTML no se llene de clases distintas.
